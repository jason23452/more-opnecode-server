# 動態 OpenCode 容器需求

## 目的

由後端 API 動態建立可透過 Cloudflare URL 存取的 OpenCode 執行環境，並管理其健康狀態與生命週期。

## 領域範圍

- 後端在部署所在主機的 Docker 上建立 OpenCode 容器。
- 容器使用固定規格，包含 curl、Python、uv、Node.js、npm、pnpm、OpenCode SDK，以及建立 Tunnel 所需的 `cloudflared`。
- 容器啟動 OpenCode 服務並監聽 `4096` port。
- 每個容器內執行 `cloudflared`，透過 Cloudflare Quick Tunnel 產生臨時 Tunnel URL，代理至該容器的 OpenCode 服務。
- 容器有獨立的暫存工作資料；刪除容器時一併清除。

## API 能力

後端需提供以下管理能力；確切路徑與 HTTP 方法留待實作設計決定：

1. **建立**：建立容器、啟動 OpenCode 與 Tunnel，等待服務健康後回傳容器識別碼及當前 Tunnel URL。初始化應有可配置逾時；逾時或初始化失敗時，清理未就緒資源並回報失敗。
2. **列表**：列出受管理的容器及其狀態與當前 Tunnel URL。
3. **單筆查詢**：依容器識別碼查詢狀態、健康狀態與當前 Tunnel URL。Tunnel URL 改變時，查詢結果應反映最新值。
4. **刪除**：停止並移除容器、終止其 Tunnel，並清除容器工作資料。

管理 API 僅供內部管理者使用，不提供使用者層級的容器所有權隔離。管理 API 的憑證或網路邊界須由部署設定保護。

## 健康監控與復原

- 以目前 Tunnel URL 的根路徑 `/` 發送 HTTP 探測；取得成功 HTTP 回應才視為外部連線健康。
- 後端需定期探測，並在達到可配置的連續失敗條件後，嘗試重建 Tunnel，避免單次網路抖動造成不必要的 URL 變更。
- Tunnel 重建成功後更新容器的當前 Tunnel URL，呼叫者透過查詢 API 取得最新 URL；不要求 webhook 或推播通知。
- 多次重建仍無法恢復時，保留容器並回報故障狀態，以供管理者查詢與處理。
- 探測週期、連續失敗次數、重試策略與初始化逾時長度應可由部署設定調整；具體預設值尚未決定。

## 安全與資源管理

- OpenCode 服務使用部署設定提供的共用密碼；密碼不應由建立 API 回傳。
- 容器的 CPU、記憶體與同時運行數量需設置可配置上限。
- 後端重新啟動後，既有容器應繼續執行；後端需重新盤點容器並恢復狀態管理與 Tunnel 健康監控。

## 驗收情境

1. 建立請求成功時，回傳的容器識別碼可查詢，且 Tunnel URL 可連線至 OpenCode `4096` 服務。
2. 初始化超時或失敗時，API 回報失敗，未就緒的容器及其暫存資料不殘留。
3. Tunnel URL 外部探測連續失敗時，系統會嘗試自動重建；新 URL 生效後，查詢 API 回傳新 URL。
4. Tunnel 多次無法恢復時，容器仍保留且查詢結果明確呈現故障狀態。
5. 刪除容器後，容器、Tunnel 與其工作資料皆已清除。
6. 後端重啟後，既有容器可重新出現在列表中，並恢復健康監控。
7. 資源限制生效；超過可配置的同時運行數量或容器資源上限時，不建立超限容器。

## 尚待實作階段確認

- OpenCode SDK 的具體套件名稱與版本，以及 OpenCode 服務的啟動方式。
- 管理 API 的路徑、回應 schema、錯誤格式，以及容器識別碼格式。
- OpenCode 密碼設定名稱與管理 API 的實際保護方式。
- 健康檢查與初始化逾時等設定的預設值。
- 容器映像建置與部署所需的 Docker 權限、網路設定及資源限制預設值。
