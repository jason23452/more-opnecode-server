# CLI prod／dev 發布與下載通道隔離

Status: ready-for-agent

## Problem Statement

目前 CLI 只在推送 `cli-v*` tag 時建置發布，後端透過單一下載來源產生 CLI 安裝指令，預設使用 GitHub 通用 Latest Release。開發者需要獨立發布開發版，並透過環境設定讓所有提供 CLI 安裝／下載資訊的 API 選擇正確版本，避免正式環境取得開發版，或開發環境誤用正式版。

## Solution

建立 prod 與 dev 兩個嚴格隔離的 CLI 發布通道：推送 `cli-v*` 發布正式版，推送 `cli-dev-*` 發布開發版。後端依 `OPENCODE_CLI_CHANNEL` 選擇對應 tag 前綴中最新發布成功且資產完整的 GitHub Release，再產生固定版本的安裝指令。

本機既有後端 `.env` 設為 `dev`；正式環境使用 `prod`，未設定時也預設為 `prod`。任何通道都不得回退至另一個通道。

## User Stories

1. 作為 CLI 維護者，我希望推送 `cli-dev-*` tag 即可發布開發版，以便提供測試版本。
2. 作為 CLI 維護者，我希望保留 `cli-v*` 的正式版發布流程，以便維持既有正式發布方式。
3. 作為 CLI 維護者，我希望開發版標記為 Pre-release 且不成為正式 Latest，以便區別兩種用途。
4. 作為 CLI 維護者，我希望測試與所有平台建置成功後才發布，以便使用者取得完整版本。
5. 作為 Windows 使用者，我希望取得對應通道的 x64 執行檔，以便直接安裝 CLI。
6. 作為 macOS 使用者，我希望 Intel 與 Apple Silicon 都有對應執行檔，以便使用原生版本。
7. 作為 Linux 使用者，我希望取得對應通道的 x64 執行檔，以便直接使用 CLI。
8. 作為開發者，我希望在 `.env` 設為 `dev` 後，管理介面取得的安裝指令使用最新 `cli-dev-*`，以便驗證開發版本。
9. 作為正式環境管理者，我希望設定 `prod` 後只使用 `cli-v*`，以便避免開發版進入正式使用流程。
10. 作為管理者，我希望未設定通道時預設為 `prod`，以便保有明確的預設行為。
11. 作為管理者，我希望通道設定錯誤時立即得到錯誤，以便避免拼字錯誤造成不預期選版。
12. 作為 API 使用者，我希望獨立安裝指令 API 與建立容器回應採用相同選版規則，以便不同入口提供一致結果。
13. 作為使用者，我希望安裝腳本與執行檔固定來自同一個 tag，以便發布新版本時不會混用資產。
14. 作為使用者，我希望重新取得並執行安裝指令即可更新至該通道最新版本，以便自行控制更新時機。
15. 作為管理者，我希望查無可用版本或 GitHub 查詢失敗時得到明確錯誤，以便排除問題且不跨通道下載。
16. 作為開發者，我希望既有自訂下載 URL 不會繞過通道限制，以便所有安裝入口都遵守隔離規則。
17. 作為部署維護者，我希望 Compose 能傳入通道設定，且文件說明發布與切換方式，以便環境設定真正生效。

## Implementation Decisions

### 發布流程

- 保留正式版 tag 觸發流程，另建開發版 GitHub Actions workflow；開發版只由 `cli-dev-*` tag 推送觸發，不以 dev 分支推送作為發布條件。
- 正式版使用 `cli-v*` tag；開發版使用原始 `cli-dev-*` tag 建立 Pre-release，不使用另一個浮動 tag 取代版本身分。
- 沿用既有 Python、PyInstaller、CLI 測試與可執行檔驗證流程，建置 Windows x64、macOS x64、macOS arm64 與 Linux x64。
- 四個執行檔及 PowerShell、shell 安裝腳本全部備妥後才完成 Release 發布。失敗或部分完成的版本不得成為 API 可選版本。
- 開發版不得標記為正式 Latest。正式版與開發版 tag 不得觸發對方的發布流程。

### 通道設定與選版

- 新增 `OPENCODE_CLI_CHANNEL`，允許值為 `prod`、`dev`，預設為 `prod`；其他值於設定載入時拒絕。
- 實作時將既有本機後端 `.env` 設為 `dev`，保留其他設定與機密；同步提供範例設定及 Compose 環境變數傳遞。實際 `.env` 不加入版本控制。
- 以同一個共用 Release 選版元件供所有相關 API 使用。`prod` 僅接受 `cli-v*` 且非 Pre-release 的版本；`dev` 僅接受 `cli-dev-*` 的版本，包含開發版流程發布的 Pre-release。
- 排除草稿、尚未發布及缺少必要資產的 Release。必要資產為現有四平台執行檔與兩種安裝腳本。
- 最新版本以 `published_at` 判定，不依版本名稱字串、Git tag 建立時間或 GitHub 通用 Latest 端點決定。處理 GitHub 分頁，避免第一頁全為其他通道時誤判沒有版本；發布時間相同時使用 Release ID 作為固定排序依據。
- 下載來源固定至選定 tag；安裝腳本 URL 與腳本使用的執行檔來源必須對應相同 Release。
- `OPENCODE_CLI_RELEASE_URL` 不再作為可繞過通道選版的任意覆寫來源。移除其在安裝指令選版路徑的作用並更新相關設定、測試及遷移說明；本規格不支援自訂鏡像來源。
- 對 GitHub 查詢設定有限逾時與短時間快取，快取以通道隔離、期限不超過 60 秒；快取有效期間可重用已驗證結果，過期查詢失敗時不使用過期結果或其他通道作為替代。

### API 整合與失敗行為

- 獨立 CLI 安裝指令 API、建立容器回應中的 `cli_install_commands`，以及實作時盤點出的其他安裝／下載資訊入口，均使用共用選版結果。
- 維持既有 API 成功回應欄位、平台參數與管理 token 驗證，不新增公開的未授權下載資訊 API。
- 無符合版本、GitHub 查詢逾時、限流或服務錯誤時，相關 API 回傳 `503` 與可理解的錯誤資訊，不產生另一通道的安裝指令。
- 建立容器流程應在產生容器副作用前確認可取得所需 CLI Release，避免因選版失敗留下使用者未取得成功回應的容器。
- 容器連線指令與上傳指令仍使用既有 `opencode-project` 命令；版本隔離發生在取得／安裝 CLI 的階段，不變更 Tunnel 資料路徑或既有 token 用途。

## Testing Decisions

- 使用者已確認以既有後端 API 測試為主要驗證邊界，模擬 GitHub Release 回應；發布流程另驗證 tag 觸發、四平台建置與 Release 資產。
- 測試外部可觀察行為：回應狀態、安裝指令中的 tag、平台資產來源及失敗時有無容器副作用，不綁定內部函式拆分或呼叫次數。
- 延伸既有建立容器與 CLI 安裝指令 API 測試，覆蓋兩通道、所有支援平台、未設定通道及非法設定。
- 以混合 Release 資料驗證：正式版較新不影響 dev、開發版較新不影響 prod；排除不匹配 tag、草稿、正式通道中的 Pre-release 與缺少資產版本。
- 驗證依發布時間而非字串排序選版、跨分頁選版，以及安裝腳本與執行檔 URL 固定在同一個 tag。
- 驗證無符合版本、GitHub 逾時、限流與錯誤回應均不跨通道回退；有效快取可重用，快取過期後能看到新版本且錯誤時不提供過期結果。
- 驗證管理 token 授權仍有效；選版失敗不建立容器。
- 沿用 CLI 安裝腳本測試，確認 API 提供的版本化來源能供現有安裝腳本使用。
- 檢查 workflow 的 tag 篩選、發布依賴、資產清單及 Pre-release／Latest 設定；在實際 GitHub Actions 執行時驗證各平台測試、建置及執行檔 `--help`。
- 自動化測試不依賴即時 GitHub 網路或真實發布；尚未觸發的 GitHub Actions 必須如實記錄為尚未執行，不能以本機設定檢查宣稱已完成遠端發布驗證。

## Out of Scope

- CLI 每次執行時自動檢查、下載或替換自身。
- 同一台電腦同時安裝兩個不同命令名稱的 CLI；本規格維持既有可執行檔名稱。
- 為前端、後端服務建立新的 dev 部署環境，或變更其映像發布與部署 tag 策略。
- 更動容器上傳、遠端 TUI 工作階段、Tunnel 或管理授權架構。
- 新增支援平台、自訂下載鏡像、歷史版本選擇介面或版本回退功能。
- 在撰寫規格階段實際推送 tag、執行發布或修改本機 `.env`。

## Further Notes

- 此處的 `prod`／`dev` 是後端設定標籤；`cli-v*`／`cli-dev-*` 是 CLI 發布的 Git tag 模式，兩者用途不同。
- 「最新」指該通道最新發布成功、符合選版條件的 Release，允許最多 60 秒快取延遲。
- 已安裝 CLI 不會因後端切換通道而自行更換版本；使用者須重新取得並執行安裝指令。此規格保證的是 API 提供的 CLI 來源通道。
- 專案採本機 Markdown issue tracker，本文件即為發布的規格；後續可依此拆分 tickets。
